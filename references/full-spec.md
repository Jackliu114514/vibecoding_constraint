# Vibe Coding 长期可维护规范开发方案

> 版本 v1.0 ｜ 2026-11-26 ｜ 适用场景：人 + Coding AI 协作的长期、复杂、多人项目

---

## 序：为什么"能跑"远远不够

Vibe coding 的诱惑是速度，陷阱也是速度。AI 能在几秒内生成看似完整的代码，但它不会替你承担三件事：**意图是否正确、边界是否安全、五年后是否还能改**。

本方案的核心命题是：

> **把 AI 的自由发挥，放进可追溯的工程契约里。**

契约由六层构成，每层回答一个具体问题：

| 层次 | 回答的问题 | 主要载体 |
|---|---|---|
| 需求 | 做什么、做到什么程度 | 需求卡、验收标准 |
| 拆解 | 分几步、每步的边界 | 任务卡、WBS |
| 架构 | 按什么边界做 | ADR 架构决策记录 |
| 风格 | 做成什么样 | Linter、Formatter、代码风格指南 |
| 追踪 | 做过什么、为什么 | Git 历史、决策日志、CHANGELOG |
| 质量 | 凭什么算好 | 测试、评审、DoD、风控 |

**三条不可妥协的底层原则**（与技术方案无关，是治理前提）：

1. **事实与推断分离** —— AI 产出中，哪些来自既有代码/原始需求，哪些是分析推断，必须显式标注。推断不得伪装成事实。
2. **单一事实来源（SSOT）** —— 每类信息只有一个权威存放处，其他位置只引用不复制。
3. **责任不可外包** —— AI 负责把事情做出来，人负责决定做什么、做到什么程度，并对结果签字担责。

## 第一部分 总体框架

### 1.1 主轴流程（八步闭环）

| 步骤 | 入口 | 核心动作 | 出口 | 主责 |
|---|---|---|---|---|
| 1. 意图收集 | 想法/问题/需求来源 | 记录原始意图，不做加工 | 原始需求条目 | 人 |
| 2. 需求澄清 | 原始需求 | AI 复述 + 列歧义 + 反问 | 需求卡（含验收） | AI 起草 / 人拍板 |
| 3. 任务拆解 | 已确认需求卡 | 拆为原子任务，标注依赖 | 任务卡列表 | AI 起草 / 人确认 |
| 4. 契约对齐 | 任务卡 + 架构约束 | 明确不改什么、怎么验 | 可执行任务（待办） | 人 |
| 5. AI 实现 | 单个任务卡 | 小步实现、即时自检 | 本地改动 | AI |
| 6. 机器自检 | 本地改动 | 测试 / lint / type / format | 自检报告 | AI（自动） |
| 7. 人工评审 | 自检通过的 PR | 逻辑、边界、架构合规判断 | 批准或退回 | 人 |
| 8. 交付记录 | 批准的 PR | 合并、更新文档与变更记录 | 可追溯交付物 | 人（AI 辅助汇总） |

> 关键：**第 2 步和第 4 步是"不可跳过关卡"**。跳过它们，等于让 AI 替你做需求决策——它不会告诉你它猜错了。

### 1.2 文件与目录约定（规范即代码）

规范文件必须进版本库，与代码同仓库、同评审、同版本。推荐结构：

```
project/
├── AGENTS.md                 # 【核心】给 Coding AI 的协作宪法，见 4.5
├── README.md                 # 项目地图，指向各权威文档
├── docs/
│   ├── requirements/         # 需求卡（一需求一文件）
│   ├── tasks/                # 任务卡 / 当前迭代看板
│   ├── adr/                  # 架构决策记录（编号递增，不可删）
│   ├── runbooks/             # 运行、部署、回滚手册
│   ├── quality/              # 质量门禁配置说明、度量看板说明
│   ├── decisions/            # 非架构类决策日志
│   └── CHANGELOG.md          # 变更记录（按版本）
├── .github/
│   ├── ISSUE_TEMPLATE/       # 需求、缺陷、任务模板
│   ├── PULL_REQUEST_TEMPLATE.md
│   └── workflows/            # CI 质量门禁
├── config/                   # lint / format / type 配置（机器可读）
└── src/
```

## 第二部分 让 AI 准确理解需求并拆解任务

### 2.1 核心机制：复述—确认循环（最容易被省略、却最有效）

在 AI 写任何代码之前，强制它输出三段话：

```
1. 我理解你要解决的问题是：（复述目标）
2. 我计划在以下边界内工作：（范围）     我明确不会改动：（范围外）
3. 完成的标准是：（可验证的验收条件）
   我不确定的点有：（歧义清单，列不出来也要写"无"）
```

**人确认后才进入实现。** 这一步把"AI 猜错 → 大段返工"前移成"AI 说错 → 一句话纠正"。

> 试想一下：如果 AI 把"导出报表"理解成"导出全部历史数据"，而你要的是"导出当前筛选结果"——在哪一阶段发现代价最小？

### 2.2 需求描述四要素（DoR：Definition of Ready）

一条需求只有同时具备四要素，才算"可交给 AI"：

| 要素 | 要写清楚什么 | 反例 |
|---|---|---|
| **上下文 Context** | 系统现状、相关模块、为什么要做 | "优化一下登录" |
| **目标 Goal** | 可度量的结果，不是动作 | "把登录页改好看" |
| **范围 Scope** | 范围内 + **范围外**（同样重要） | 只说"实现导出" |
| **验收 Acceptance** | Given/When/Then 可判定条件 | "体验要好" |

补充要素：依赖、约束（技术/合规/时间）、开放问题、事实/推断标注。

### 2.3 任务拆解的三级粒度

```
Epic（一个业务目标，跨多个迭代）
  └── Story（一个可交付的用户价值）
        └── Task（一次提交可完成、一个可验证结果）
              └── Prompt（给 AI 的单条可执行指令）
```

**原子任务的四条硬标准：**

1. **单一职责** —— 一个任务只改一个关注点，不混合"重构 + 加功能 + 改配置"。
2. **可独立验证** —— 有明确命令或条件能判断完成（测试通过 / 接口返回预期）。
3. **一次提交可容纳** —— 拆到 diff 能在一个 PR 内被人类读完（建议 ≤ 400 行）。
4. **依赖显式** —— 明确"必须先完成 X"，禁止隐含顺序。

### 2.4 给 AI 的指令编写规范

一条合格的 Prompt 必须包含五段（可复用附录 B3 任务卡结构）：

```
【角色】 你是一个有 5 年经验的后端工程师，熟悉本项目分层架构。
【上下文】 现有 order 模块位于 src/order/，使用 Repository 模式，见 docs/adr/0003。
【任务】 为订单导出增加"仅导出当前筛选结果"能力。
【边界】 只改 src/order/export.ts 及其测试；不要修改数据模型；不要引入新依赖。
【验收】 传入 filter 参数时，仅返回匹配记录；无 filter 时保持原行为；新增单测覆盖两种分支。
【不确定处理】 若以上信息不足，先列出问题，不要自行假设后直接写代码。
```

**禁止事项**：不要说"参考类似实现"（AI 会臆造）、不要省略范围外、不要用"等等"这类模糊后缀。

### 2.5 事实与推断标注（务必写进 AGENTS.md）

AI 的分析、总结、评审意见中，必须区分：

- **【原文】/【既有】**：来自需求文档、现有代码、既有配置的确定信息。
- **【分析结论，非原文】**：AI 或人的推断、判断、建议。

这条规则直接消灭 vibecoding 中最隐蔽的风险：**AI 把自己的猜测写成既定事实，人据此做了错误决策。**

## 第三部分 规范体系（需求 / 架构 / 风格 / 提交 / 文档）

### 3.1 需求描述规范

- 一需求一文件，文件名为 `REQ-<编号>-<短标题>.md`。
- 状态机：`草稿 → 待澄清 → 已确认 → 已拆解 → 进行中 → 已验收 / 已废弃`。
- 变更需求必须修改原需求卡并留痕，禁止在聊天记录里"口头改需求"。
- 验收标准一旦确认，实现阶段不得单方面放宽。

### 3.2 架构约束与 ADR（Architecture Decision Record）

**什么时候必须写 ADR：**
- 引入新依赖、新服务、新数据模型；
- 改变模块边界、通信方式、存储方案；
- 做出有长期维护代价的取舍（如用缓存换一致性）；
- 推翻或替代既往决策。

**ADR 状态**：`提议 Proposed → 接受 Accepted → 已替代 Superseded / 废弃 Deprecated`。已接受的 ADR **不可删除**，被替代时新建一条并指向旧条目。

详见附录 B2。

### 3.3 代码风格规范

**原则：能被机器检查的，绝不写进文档让人肉眼看。**

| 类别 | 工具 | 强制方式 |
|---|---|---|
| 格式化 | Prettier / gofmt / black | 提交前自动执行 |
| 静态风格 | ESLint / Ruff / Checkstyle | CI 阻断（error 级） |
| 类型 | TypeScript / mypy / 类型注解 | CI 阻断 |
| 依赖安全 | npm audit / Dependabot | 高危阻断 |
| 提交信息 | commitlint | 提交时校验 |

文档只保留**机器无法判断的约定**：命名语义、分层职责、错误处理约定、模块依赖方向。

### 3.4 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>

<body：说明为什么，而非做了什么>

<footer：Refs: REQ-1024 | BREAKING CHANGE: ...>
```

type 枚举：`feat` 新功能 / `fix` 修复 / `refactor` 重构 / `test` 测试 / `docs` 文档 / `chore` 构建配置 / `perf` 性能 / `revert` 回滚。

**规则**：
- 一个提交对应一个任务卡（`Refs:` 必须能追溯到需求）。
- subject 用祈使句、小写、不超过 50 字符。
- AI 生成的提交必须在 body 注明 `Assisted-by: <AI 工具/版本>`（便于统计与追责）。

### 3.5 文档规范

| 文档 | 更新时机 | 责任 |
|---|---|---|
| README | 项目结构/启动方式变化时 | 人确认，AI 起草 |
| ADR | 架构决策产生时 | 人批准，AI 记录 |
| 需求卡 | 需求澄清/变更时 | 人拍板，AI 整理 |
| CHANGELOG | 每个版本发布时 | AI 汇总，人核对 |
| Runbook | 部署/回滚流程变化时 | 人编写并演练 |

**铁律：改代码不改文档，PR 不予合并。** 文档漂移是长期项目腐化的第一信号。

## 第四部分 长期复杂项目的可追踪与可管理

### 4.1 三个单一事实来源

| 信息类型 | 唯一权威来源 | 其他位置 |
|---|---|---|
| 需求是什么 | `docs/requirements/` 中的需求卡 | 任务卡只引用 ID |
| 为什么这么设计 | `docs/adr/NNNN-*.md` | 代码注释只写"为什么"的摘要并链接 ADR |
| 发生了什么变更 | Git 历史 + `CHANGELOG.md` | 聊天记录不作为依据 |

**推论**：任何只存在于对话上下文里的决策，等于不存在。AI 会忘，人会忘，仓库不会。

### 4.2 任务状态机

```
待定义 → 已澄清 → 已拆解 → 进行中 → 待评审 → 已完成
                                  ↓
                               已阻塞（记录阻塞原因与解除条件）
```

每次站会/迭代只需看三个数：**各状态任务数、阻塞时长、超期任务数**。

### 4.3 决策日志与变更记录

- **决策日志**：记录非架构类判断（如"为什么选这个第三方库而不自研"），格式同 ADR 精简版。
- **变更记录**：按版本组织，每条变更必须能反查到 `Refs:` 需求编号，格式见附录 B6。

### 4.4 AI 上下文管理（长期项目特有风险）

- 每个会话开始，让 AI 先读 `AGENTS.md` + 相关 ADR + 当前任务卡，再动手。
- 单次会话只处理一个任务；跨会话交接靠任务卡状态，不靠"记住上次聊到哪"。
- 定期（每迭代）让 AI 审查文档与代码是否一致，输出差异清单。

### 4.5 AGENTS.md 模板要点（AI 协作宪法）

必须包含：项目地图、不可违反的架构规则、代码风格入口、提交格式、事实/推断标注要求、任务开始前的复述确认要求、禁止操作清单（如禁止改数据库 schema、禁止引入新依赖需先 ADR）。

## 第五部分 代码质量保障体系

### 5.1 五道质量关卡

| 关卡 | 检查内容 | 执行者 | 不通过处理 |
|---|---|---|---|
| G1 需求关卡 | 需求卡四要素齐全、验收可测 | 人 | 退回澄清 |
| G2 静态关卡 | lint / format / type / 依赖安全 | AI 自动（CI） | 阻断，AI 自行修复后重跑 |
| G3 测试关卡 | 单元测试、集成测试、覆盖率门槛 | AI 自动（CI） | 阻断，补测 |
| G4 评审关卡 | 逻辑、边界、架构合规、可读性 | AI 初筛 + 人终审 | 退回任务卡 |
| G5 验收关卡 | DoD 全部满足、文档已更新、变更已记录 | 人 | 不予合并 |

### 5.2 测试策略

- **测试金字塔**：单元测试为主 → 集成测试覆盖关键链路 → 端到端测试覆盖核心用户路径。AI 尤其擅长批量生成单测，但**测试用例的"预期值"必须由人确认**。
- **AI 写测试的纪律**：先写测试再写实现时，测试必须来源于验收标准，不能从实现反推（否则只是给错误实现盖章）。
- **覆盖率门槛**：新增代码行覆盖率 ≥ 80%（按项目调整），核心模块 ≥ 90%。覆盖率是底线不是目标。
- **回归保护**：每次修复缺陷必须附加一条能复现该缺陷的测试。

### 5.3 静态检查

所有检查必须**本地可跑、CI 强制、配置入库**。本地通过是提交前提，CI 通过是合并前提。AI 应在提交前自行运行并修复，人不需要重复做机器能做的事。

### 5.4 代码评审（AI 初筛 + 人终审）

- **AI 初筛**：检查格式、命名、明显逻辑漏洞、缺失测试、与 ADR 冲突、提交信息规范，输出结构化清单。
- **人终审**：只聚焦机器判断不了的事——业务逻辑是否符合真实意图、边界与安全、架构权衡是否可接受、是否引入了隐性技术债。
- **原则**：人不做 AI 能做的检查，AI 不做需要担责的判断。

### 5.5 完成定义（DoD）

一个任务只有全部满足才算完成：

- [ ] 代码已合并，且对应任务卡状态为"已完成"
- [ ] G2/G3 全部通过（附 CI 链接）
- [ ] 人工评审通过，无未解决的阻断性意见
- [ ] 相关文档（README / ADR / Runbook）已同步更新
- [ ] CHANGELOG 已登记，含需求编号
- [ ] 无 P0/P1 未修复缺陷
- [ ] 技术债若有新增，已登记并有人接受

## 第六部分 人工与 AI 的评审职责

### 6.1 RACI 矩阵（R=执行 A=最终负责 C=咨询 I=知会）

| 活动 | AI | 人 |
|---|---|---|
| 需求复述与歧义列举 | **R** | A |
| 需求目标与优先级拍板 | C | **A/R** |
| 任务拆解草案 | **R** | A |
| 任务边界确认 | C | **A/R** |
| 架构方案提议 | **R** | A |
| 架构决策批准 | C | **A/R** |
| 代码实现 | **R** | A（通过评审） |
| 静态检查与测试执行 | **R** | I |
| 代码评审初筛 | **R** | A |
| 代码评审终审与放行 | I | **A/R** |
| 合并生产分支 | I | **A/R** |
| 变更记录汇总 | **R** | A（核对） |
| 风险接受与技术债确认 | C | **A/R** |

### 6.2 AI 不得单独决定的红线

以下事项**必须有人签字**，AI 只能提供建议：

1. 需求范围变更与验收标准放宽
2. 架构决策（尤其数据模型、模块边界、外部依赖引入）
3. 生产环境合并与发布
4. 安全相关逻辑（鉴权、加密、权限）的实现方案
5. 技术债的接受与偿还优先级
6. 对缺陷严重等级的判定

## 第七部分 完成度、里程碑交付与风险控制

### 7.1 项目完成度度量（建议每迭代采集）

| 维度 | 指标 | 计算方式 | 健康信号 |
|---|---|---|---|
| 范围完成 | 需求完成率 | 已验收需求数 / 计划需求数 | 随迭代稳定上升 |
| 质量 | 评审一次通过率 | 首轮通过 PR 数 / 总 PR 数 | ≥ 70% |
| 质量 | 缺陷逃逸率 | 生产缺陷数 / 总缺陷数 | 持续下降 |
| 质量 | 新增代码覆盖率 | 覆盖行 / 新增行 | ≥ 80% |
| 效率 | AI 产出采纳率 | 直接合并行数 / AI 生成行数 | 趋势上升 |
| 可维护 | 技术债增量 | 新增未偿条目数 | 不持续为正 |
| 可追溯 | 文档同步率 | 通过文档检查的 PR 占比 | 100% |

> **为什么同时看"采纳率"和"一次通过率"？** 采纳率高但一次通过率低，说明 AI 产出量大却质量差，人在替它返工——这是 vibecoding 最典型的质量幻觉。

### 7.2 里程碑定义与准入/准出

| 里程碑 | 交付物 | 准入条件 | 准出（验收）条件 |
|---|---|---|---|
| M0 基线建立 | AGENTS.md、规范体系、CI 门禁、目录骨架 | 团队对规范达成一致 | 首个任务能跑通全流程 |
| M1 骨架可运行 | 核心模块骨架、ADR 首批、Runbook 初版 | M0 准出 | 本地可启动，CI 全绿 |
| M2 核心功能 | P0 需求全部验收 | M1 准出 | 需求完成率 P0=100%，DoD 全通过 |
| M3 质量加固 | 测试补全、技术债清理、文档齐备 | M2 准出 | 覆盖率达标，P0/P1 缺陷清零 |

### 7.3 风险登记册（常见风险与对策）

| 风险 | 触发信号 | 预防措施 | 应对措施 | 责任人 |
|---|---|---|---|---|
| 需求漂移 | 实现中频繁改验收标准 | DoR 门槛、变更需改需求卡 | 回滚到已确认版本，重新评审 | 人（需求方） |
| AI 过度实现 | diff 超出任务范围 | 任务卡写清范围外、单任务单提交 | 拆分提交，剔除越界改动 | 人（评审） |
| 上下文丢失 | 会话切换后重复解释 | AGENTS.md + 任务卡交接 | 新会话先读上下文再动手 | 人 + AI |
| 技术债累积 | 债务条目持续增加 | 每迭代预留偿还额度 | 登记、排序、纳入里程碑 | 人（技术负责人） |
| 文档漂移 | 文档同步率 < 100% | PR 模板强制文档勾选 | 不通过合并，补文档 | 人（评审） |
| 质量幻觉 | 高采纳率 + 低一次通过率 | 评审一次通过率纳入门禁 | 加强 G4 人工终审 | 人（评审） |
| 安全合规 | 鉴权/加密逻辑由 AI 独自决定 | 列入红线清单 | 强制人工评审 + 安全测试 | 人（安全负责人） |

## 结语：如何判断这套规范真的在起作用

不是看文档写得多漂亮，而是看三个问题能否被回答：

1. 三个月前某个决定**为什么**这么做——能在 ADR 里找到吗？
2. 某行代码**对应哪条需求**——能从提交 `Refs:` 反查到吗？
3. AI 生成的代码出了问题——能说清**哪一步评审本该拦住它**吗？

如果三个答案都是"能"，这套规范就活了。否则，它只是一份没人看的文档。
