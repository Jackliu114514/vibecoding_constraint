# AGENTS.md — 本项目 AI 协作规则

> 使用方式：复制到你的项目**根目录**，按 `<按项目填写>` 处补齐。
> 这份文件是给 Coding AI 的协作宪法——每次会话开始，AI 必须先读它。

---

## 一、开工前必读

每次接到任务，按顺序读取：

1. `README.md` —— 项目结构与启动方式
2. `docs/adr/` 中与本次任务相关的 ADR —— 不可突破的架构边界
3. 当前任务卡（若已提供）—— 改动范围与验收标准
4. 若信息不足，**先提问**，不要靠猜测补全。

---

## 二、复述确认（硬性，不可跳过）

拿到任务后，**先输出以下五段，等用户确认后再写代码**：

```
1. 我理解你要解决的问题是：
2. 我计划的改动范围是：
3. 我明确不会改动的是：
4. 完成的判定标准是：
5. 我不确定的点有：（没有问题也要写"无"）
```

收到"确认"之前，不得开始实现。用户口头补充的变更，必须回填到任务卡后才生效。

---

- 未经 ADR 批准，不得引入新依赖。
- 不得改动数据库 schema，除非任务卡明确要求且已有对应 ADR。

- 其他禁止事项：<按项目填写>

## 四、代码风格与检查

- 提交前必须运行：`<按项目填写，例如 npm run lint && npm test>`
- 格式化工具：`<按项目填写，例如 prettier>`，不得提交未格式化代码。
- 命名与分层语义约定：<按项目填写，例如 "服务层只做编排，不写业务规则">
- 不写解释"做了什么"的注释；注释只写"为什么"。

---

## 五、事实与推断（必须遵守）

在一切分析、总结、评审意见中，必须区分：

- **【原文】/【既有】**：来自需求文档、现有代码、配置的确定信息。
- **【分析结论，非原文】**：你的推断、判断、建议。

推断不得伪装成事实。不确定就明确说不确定，并列出需要人工确认的点。

---

## 六、提交格式

```
<type>(<scope>): <subject>

<说明为什么，而非做了什么>

Refs: REQ-<编号> / TASK-<编号>
Assisted-by: <工具名称及版本>
```

type 取值：`feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `perf` / `revert`。
一个提交只对应一个任务卡，不混合多个关注点。

---

## 七、禁止事项

- 不改动任务卡写明范围外的文件。
- 不用"参考类似实现"作为依据——你可能会臆造不存在的代码。
- 不自行放宽验收标准。
- 不自行决定架构变更、需求范围、发布合并。
- 不把推断写成既定事实。
- 不在一次提交里混合"重构 + 新功能 + 改配置"。

---

## 八、完成任务时的输出

每次任务结束，输出以下五项：

1. **改动清单**：改了哪些文件，每个文件改了什么。
2. **自检结果**：运行了哪些命令，通过情况。
3. **偏差说明**：与原计划有何不同，为什么。
4. **遗留风险**：未解决的问题、可能的技术债。
5. **待人工确认**：需要人拍板的具体事项。

---

> 记住：你负责把事情做出来；人负责决定做什么、做到什么程度，并对结果签字担责。
